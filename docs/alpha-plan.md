# Takki — Alpha Execution Plan

Session-by-session breakdown of [Alpha](roadmap.md#alpha--internaldev-only). Sequencing only — architecture is decided in [architecture.md](architecture.md) and the ADRs. This plan exists so each working session opens here, picks the next unchecked row, does exactly that chunk, commits, and closes.

**Working model:** one session = one chunk = one model = one commit. Strict dependency order; no parallel lanes. Each chunk is a vertical slice — `typing.Protocol` + real implementation + fake in `tests/fakes/` land together (per [ADR-019](adr/0019-testing-strategy-and-io-isolation.md), roadmap line 95). A chunk commits only on green tests.

**How to use this file**
1. Open the session table, find the first unchecked row.
2. Launch a Claude Code session with the **model** named in that row.
3. Implement only that chunk. Check the relevant carry-forward decisions first (see below).
4. On green, run `/code-review` (step 6), sweep the findings (step 5), then **you** commit, tick the box, fill in the commit SHA, and close the session. Generated session prompts stop at green + clean review + filed findings, and leave staging/commit to you.
5. **Findings sweep — every session, after the review and before handing back.** Go back over what the session surfaced that is not already fixed in code or written into an ADR it amended: places two accepted ADRs disagree, assumptions only confirmable on Windows, behaviour a later session must verify or could unknowingly undo, and decisions taken that no ADR records. Each one either dies with the session — drop it — or has to reach a later session, and then it gets filed where that session will actually look:
    - an amendment in the ADR section whose reader needs it, dated and attributed to the session (the default, and the most likely to be read);
    - [roadmap.md](roadmap.md) § B for a genuine conflict between two accepted ADRs, § D for a smaller gap worth a line;
    - the carry-forward table below when it gates one specific numbered session, or that session's own row when it is a hand-verification item.

    Use those documents; do not create new ones, and do not file something already fixed and covered by a regression test. A finding that exists only in the session's chat report is lost. Generated session prompts carry this step in their finish line, and pass it on to the prompt they draft for the next session.
6. For Sonnet/Haiku chunks, run `/code-review` (medium/high effort) in-session before handing back — same context, no separate review session. Escalate to an Opus pass only if it flags something structural.

**Model strategy.** Opus is reserved for the judgment chunks (the focus state machine and the engine core, #6–#10, plus Windows interpretation #12a–12b), where a subtle slip silently corrupts progression math or input handling. Everything else is specced tightly enough by the ADRs for Sonnet; scaffolding goes to Haiku. **Tripwire:** if a Sonnet chunk starts needing real architectural decisions mid-session, that is a signal the ADR underspecified it — stop, tighten the spec (or promote the chunk to Opus) rather than letting the model guess.

| 12a-1 | **Windows layout reader.** `WindowsPlatformInterface.get_layout_positions()` — scan codes → `Layout`. The judgment half of the old #12a, and now the whole of this row. **It takes no arguments and checks nothing:** it reports what the machine has, and `main.verify_layout` — already built — decides whether that can teach the configured language. Keeping the two apart is what makes the reader testable at all: a reader told to expect `en` is one plausible refactor from returning `build_en()` when a scan code reads oddly, and reporting a German keyboard *truthfully* is the one case it exists for. **The work is the grid, not the characters.** Windows gives the character half live — `ToUnicodeEx` against an `HKL` — but no geometry: scan codes are a flat positional space with no row or column. The scan-code→(row, col) table is therefore hard-coded here and **must agree with `build_en()` exactly**, because `COL_TO_FINGER` is a pure function of `col` — an off-by-one column does not merely move a letter, it reassigns fingers and re-pairs Phase 1's symmetric slots. Three more decisions in the same function: `ToUnicodeEx` mutates keyboard state and returns a negative count on a dead key (Icelandic `0x40f` is installed on the laptop, so this is live, not hypothetical); **what the reader filters out** — emit digits and punctuation and `key_positions()` carries ~20 entries `build_en()` lacks, so Takki refuses to start on a *correct* keyboard; and keys returning more than one character on ligature layouts, which is one rule to settle, not a layout to test. **`Layout.lang` is the keyboard's language, not the system locale** — HKL low word masked `& 0x3FF`, the same reduction `language_for_lcid` already applies to SAPI tokens. Full KLID precision is never compared anywhere: `0x409` and `0x809` are both `en`, and Takki teaches only letters ([ADR-006](adr/0006-language-and-keyboard-layout-scope.md)), so a UK keyboard must pass — which is why `describe_mismatch` compares positions and not layout identity. `GetKeyboardLayout(0)` returns the **calling thread's** layout; ours is the right one only because our window is the focus anchor ([ADR-028](adr/0028-composite-input-and-keyboard-ownership.md)) — comment it where the call lands. **Take the `HKL` as a parameter, which is what makes this CI-testable** *(2026-09-20 review)*: `ToUnicodeEx` and `MapVirtualKeyEx` both accept one, and `LoadKeyboardLayout(klid, KLF_NOTELLSHELL)` loads any layout Windows ships — the DLLs and their `Control\Keyboard Layouts` entries are present on a stock install — with no admin, no change to the user's language list and no activation.
