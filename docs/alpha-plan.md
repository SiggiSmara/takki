# Takki — Alpha Execution Plan

Session-by-session breakdown of [Alpha](roadmap.md#alpha--internaldev-only). Sequencing only — architecture is decided in [architecture.md](architecture.md) and the ADRs. This plan exists so each working session opens here, picks the next unchecked row, does exactly that chunk, commits, and closes.

**Working model:** one session = one chunk = one model = one commit. Strict dependency order; no parallel lanes. Each chunk is a vertical slice — `typing.Protocol` + real implementation + fake in `tests/fakes/` land together (per [ADR-019](adr/0019-testing-strategy-and-io-isolation.md), roadmap line 95). A chunk commits only on green tests.

**How to use this file**
1. **Close the previous session, then find the first unchecked row.** *(Added 2026-11-13.)* The developer reviews and commits after a session has ended, so the session that did the work cannot record its own commit. The next session does it, before anything else:
    - Run `git status` and `git log`. If the previous session's work is committed, take that session as done. If its work is still uncommitted in the working tree, stop and tell the developer; do not start new work on top of it.
    - Tick the previous session's row and fill in the commit's short hash. A row split into several sessions (#12m) gets each session marked done with its commit in the split note, and is ticked with its last session.
    - **Collapse it.** Reduce the ticked row to one line: what it built, its spec links, the commit. Delete the notes under the table that it wrote or that were addressed to it, and any carry-forward row whose gated sessions are now all ticked. Before deleting each item, check that it is either done or filed where step 5 says (an ADR, the roadmap, or a row still open); if it is neither, file it first. Notes addressed to a session still open stay. When unsure, keep the item and say so in the session's report.
    - Nothing is copied to another file. Git keeps every earlier version of this plan (`git log -p docs/alpha-plan.md`), and an archive file would return stale text to every search.
    - These edits are committed with the new session's own work. Generated session prompts open with this step. The last row has no next session; whoever reads its results ticks it.
2. Launch a Claude Code session with the **model** named in that row.
3. Implement only that chunk. Check the relevant carry-forward decisions first (see below).
4. On green, run `/code-review` (step 6), sweep the findings (step 5), then **you** review, commit and close the session. The tick, the commit hash and the collapse are the next session's first step (step 1). Generated session prompts stop at green + one review pass with its findings fixed or filed + filed findings, and leave staging/commit to you. *(Changed 2026-11-08: prompts used to say "re-run until clean". The ADR-032 session ran 17 passes over mostly prose, each finding something new to reword. Now one review per developer message, enforced by a hook; see step 6.)*
5. **Findings sweep — every session, after the review and before handing back.** Go back over what the session surfaced that is not already fixed in code or written into an ADR it amended: places two accepted ADRs disagree, assumptions only confirmable on Windows, behaviour a later session must verify or could unknowingly undo, and decisions taken that no ADR records. Each one either dies with the session — drop it — or has to reach a later session, and then it gets filed where that session will actually look:
    - an amendment in the ADR section whose reader needs it (the default, and the most likely to be read). **The amendment replaces the text it changes**, so the section still reads as the current design, and it adds one line to the change list at the end of the ADR: date, session, what changed. It is not appended as a dated note beside the old text. CLAUDE.md's *ADRs state the current design* rule has the whole of it. *(Changed 2026-11-13: this bullet used to say "dated and attributed to the session", and every session appended. ADR-024 grew from 14 KB to 111 KB that way, and a reader had to replay the dates to learn what holds.)*
    - [roadmap.md](roadmap.md) § B for a genuine conflict between two accepted ADRs, § D for a smaller gap worth a line;
    - the carry-forward table below when it gates one specific numbered session, or that session's own row when it is a hand-verification item.

    Use those documents; do not create new ones, and do not file something already fixed and covered by a regression test. A finding that exists only in the session's chat report is lost. Generated session prompts carry this step in their finish line, and pass it on to the prompt they draft for the next session.
6. Review as CLAUDE.md's *Code review* rule says: propose level and model, then one pass. A Sonnet review is `/code-review` in-session; an Opus review is a separate Opus session that reviews alone and hands its findings back; the coding session fixes them and has Sonnet review the fixes. After the pass, fix the findings, then stop and report what another pass would likely bring; the developer decides whether to run it. Generated prompts say "one review pass", never "until clean". *(Changed 2026-11-08: Opus review agents never finished clean and used up the session allowance.)*

**Model strategy.** Opus is reserved for the judgment chunks (the focus state machine and the engine core, #6–#10, plus Windows interpretation #12a–12b), where a subtle slip silently corrupts progression math or input handling. Everything else is specced tightly enough by the ADRs for Sonnet; scaffolding goes to Haiku. **Tripwire:** if a Sonnet chunk starts needing real architectural decisions mid-session, that is a signal the ADR underspecified it — stop, tighten the spec (or promote the chunk to Opus) rather than letting the model guess.
